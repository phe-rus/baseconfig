# Discussion log

Running log of the design conversation for BaseConfig (named Demoness until 2026-09-04 — see that entry below). Append dated entries; don't rewrite history — if a decision changes, add a new entry noting the change and why, rather than editing the old one away. Entries dated before 2026-09-04 say "Demoness" throughout because that was the project's real name at the time; this is left as-is rather than retroactively renamed, per this file's own rule.

## 2026-08-31 — Initial vision

Kickoff framing, roughly as given:

- PayloadCMS's *approach* is the model to borrow from (config-driven collections, auto-generated admin UI, hooks, access control) — but not the stack. Payload is Next.js, heavy, and pushes a paid cloud tier; it was never built for Cloudflare Workers/Pages.
- A prior attempt to build something similar directly inside `infra` or `seer` didn't land well and wasn't performing on par with what's needed — hence splitting this into its own project.
- New project name: **Demoness**, in its own monorepo at `~/projects/demoness`, fully open source.
- Explicit process requested: discuss everything first, then design (still no code), then figure out the dev approach, and only then start coding. This log and `CLAUDE.md` exist so that process survives across sessions instead of restarting each time.
- Preferred stack, stated directly: TanStack Start fully (all of its ecosystem — Router, Query, Store, Form, DB, etc.), Zod as the schema builder, D1, R2, KV, edge caching.
- Wants visual drag-and-drop editing, Payload-style, with a design concept inspired by Apple Freeform's app design and overall feel.
- Wants to reuse `infra` for auth/OAuth rather than rebuilding identity.
- Multi-tenancy: needs a strategy for "multi D1 into one D1" so the system can start simple and expand — i.e., a concrete story for scaling from a single shared database toward per-tenant or sharded databases without a rearchitecture. Needs to support single-tenant and multi-tenant use from day one.
- Rich text / editor approach: still to be discussed in CMS-specific terms, but the existing project rule (no third-party rich-text libraries, build on primitive DOM/contentEditable) is the working assumption carried over from `seer`.
- Role-based access: different people should be able to manage different sites/content with different permission levels — shape not yet decided.
- Mentioned wanting AI involved, without specifics yet.
- Target scale for staying entirely on Cloudflare's free plan: roughly 100 pages, 1000 blog posts, lots of images, and 500 active users, for a meaningful stretch of time before needing to pay for anything.

Nothing here is a locked decision yet — this is the opening framing the rest of the discussion phase works from. See `CLAUDE.md` for the running "open questions" list this should resolve into.

## 2026-08-31 — First round of decisions

Answers to the five open questions raised after the kickoff:

1. **D1 strategy: hybrid/sharded.** Start on one shared D1, shard out per tenant as they outgrow it. D1 free tier is 500 MB/database, 5 GB/account, 10 databases/account — confirmed via Cloudflare docs, so this isn't premature optimization, it's a real ceiling.
2. **Visual editing: freeform canvas is the default view**, with a switch to raw JSON view of the same content, and a switch to an API view showing the actual request/response. Three views, one underlying model.
3. **AI: in scope, provider-agnostic.** Ship with Workers AI and Gemini's free tier as initial providers; the provider layer must be pluggable so any other model/provider can be added later without a rearchitecture. Which AI *features* to build is still undecided.
4. **License: the Pherus Parley License.** Custom, MIT-based, named and themed after the Pirates of the Caribbean Code/Parley concept and Lord of the Mysteries. Decision on name and spirit only — actual clause text is a later step.
5. **Confirmed real Cloudflare free-tier numbers** (see `CLAUDE.md`'s table). Workers (100K req/day, 10ms CPU) and KV (1K writes/day) are the tight constraints; D1 and R2 have comfortable headroom for the stated target. The plan only works if rendered pages are served from edge cache on the common path and KV writes stay infrequent (KV reserved for sessions/small stuff only — confirmed).

## 2026-08-31 — Corrected: single D1, no sharding, tenancy via Organization plugin

Walked back the two-DB and sharded-multi-D1 plans above after clarifying the actual model: **one single D1 database**, no split. Auth uses better-auth wired to `infra`'s OAuth as the identity provider — the same pattern `seer` already runs (`export const auth = betterAuth({...})`) — plus an admin plugin. Sharding to multiple databases is now a future escalation path only, not the starting architecture — most of the earlier open questions about sharding triggers and shard routing are moot for now.

## 2026-08-31 — Collections/Globals as Zod configs; canvas redefined as a map, not the editor

Two decisions:

1. **Collections and Globals, exactly Payload's concepts** (repeatable types vs. singletons), authored as Zod-based "configs" — the term Demoness uses in place of Payload's field DSL. Same single-source-of-truth principle: one config generates DB schema, admin UI, and API together.
2. **The freeform canvas isn't the editing surface — it's a map/overview.** Revised from the earlier "freeform is the default editing view" decision: the canvas is a freely-arrangeable live overview of all pages (live-preview thumbnails, user-controlled ordering/positioning, shows connected structure to the Collections/Globals each page draws from — select a page to see and edit its connected configs). Actual editing of a Collection/Global item uses **Payload's Live Preview** pattern instead: fields on one side, live-rendered output updating in real time on the other. JSON view and API view still apply as alternate views of an item alongside Live Preview. Open: exactly how the map visualizes "connected structure," and how thumbnails stay current.

## 2026-08-31 — No Cloudflare Images; publish-triggered edge caching, speed as an explicit goal

- **No Cloudflare Images** — too expensive. R2 only, well-structured (exact key/folder scheme still to be worked out). Image-improvement AI features route through Workers AI or another pluggable model instead of Cloudflare Images' transform API.
- **Caching model, decided**: the whole platform is edge-cached by default. Cache is populated/invalidated only when a publisher/editor actually publishes or updates — not on a timer, not per-request revalidation. Every other read (normal visitor traffic) is served from the edge cache, never touching D1 or backend logic. This is the concrete mechanism behind the earlier "must cache aggressively to fit the free tier" advice — now it's an actual decision, not just a constraint to keep in mind.
- **Extremely fast load times are an explicit goal**, not incidental — the cache-first model serves both the free-tier budget and the speed goal at once.

## 2026-08-31 — Dev approach: package structure, routing split, API surface, group() field type

First round of the "dev approach" discussion phase (design mockups are done — see the published canvas — this is architecture before code, per the discuss → design → dev approach → code order).

- **Monorepo package split, decided**: `packages/ui` (existing shadcn primitives) stays. New packages, folder name → npm scope: `demoness-fields/` (`@demoness/fields` — field-type definitions: Zod schemas + admin component mapping), `demoness-core/` (`@demoness/core` — `defineCollection`/`defineGlobal`, access control, hooks, generates DB schema + API + admin manifest from a config), `demoness-d1/` (`@demoness/d1` — Drizzle schema/client, migrations), `demoness-r2/` (`@demoness/r2` — asset upload, key scheme, serving), `demoness-ai/` (`@demoness/ai` — the one unified AI provider abstraction). Dependency order: `fields` → `core` → (`d1`, `r2`, `ai` as siblings `core` calls into) → `www` consumes everything plus `ui`.
- **ORM: Drizzle**, confirmed — D1-native, supports local-first dev via wrangler.
- **Payload-shape question resolved**: borrow Payload's *concepts* (fields, blocks, access API shape) but implement them the way Zod and TanStack idioms naturally want, not literal Payload API parity. This is why the field-config package is `@demoness/fields` rather than trying to be a Zod-flavored clone of Payload's own field DSL.
- **API surface: both.** Server routes (real HTTP endpoints, e.g. `GET /api/pages/:slug` — the public headless API, matches the API tab in the mockups) *and* TanStack Start server functions (for admin-internal calls) both stay in play — not one at the expense of the other. Both are thin wrappers over the same `@demoness/core` access-controlled operations, so there's one source of truth underneath regardless of which transport is used.
- **Routing/deployment: one app, one Worker, one deployment.** `/admin/*` is the dashboard (everything mocked in the canvas: Dashboard, Pages/Posts/Users lists, Edit's Hero/Layout/SEO/Settings tabs, Media, Headers, Site Settings) — authenticated, never edge-cached. `/` and everything else is the actual public site, rendering a page by walking its `layout` blocks through per-block-type renderers (the render-side counterpart of the Layout block system in the mockups). Cache rules must explicitly exclude `/admin/*` from the cache-first path decided in the entry above.
- **Field taxonomy: adopt Payload's full field-type list**, confirmed against Payload's own docs (payloadcms.com/docs/fields/overview) rather than inferred from the mockups alone — the earlier two passes at this list were both wrong (first too short, second invented two field types, `tags` and `slug`, that Payload doesn't actually have as distinct types):
  - **Data fields** (produce a DB column): `array`, `blocks`, `checkbox` (boolean), `code` (code-editor string), `date`, `email`, `group` (named), `json`, `number`, `point` (geo coordinates), `radio`, `relationship` (single or hasMany), `richtext`, `select` (single or hasMany), `tabs` (named), `text`, `textarea`, `upload`.
  - **Presentational fields** (admin-layout only, no DB column): `collapsible`, `row` (lay fields side by side), `tabs` (unnamed), `group` (unnamed), `ui` (blank slot for a fully custom admin component).
  - **Virtual**: `join` — computed two-way relationship (e.g. list every Post referencing an Author without storing the FK on the Author side); not backed by its own column.
  - **What the mockups actually map to, corrected**: Settings' "Tags" pills → `select` with `hasMany: true`, not a bespoke tags type. Settings' "Slug" (auto-derived from Title, editable, lock icon) → a plain `text` field with a custom admin component + a `beforeValidate`-style hook, matching Payload's own website-template pattern — also not a distinct field type. Hero's "Type" pill row and the Link field's "Link Type" toggle → `radio`. Hero's richtext area → `richtext`. Column Width and Appearance selects → `select`.
  - **Design insight, still holds**: Hero/Layout/SEO/Settings are best modeled as one named `tabs` field on the Pages collection config, not four separate top-level concerns — each tab just holds its own field set (Hero tab → a `group`, Layout tab → the `blocks` array, SEO tab → the plugin's fields, Settings tab → title/slug/parent/tags/authors).
- **Hooks, adopted at three tiers, confirmed against Payload's hooks docs** (payloadcms.com/docs/hooks/*):
  - **Collection hooks** (full CRUD lifecycle, in firing order): `beforeOperation` → `beforeValidate` (create/update) → `beforeChange` (create/update, data still unvalidated at this point) → *validation happens* → `afterChange` → `beforeRead` → `afterRead` → `beforeDelete` → `afterDelete` → `afterOperation`.
  - **Global hooks**: the same shape minus delete (a global is one singleton document, nothing to delete): `beforeOperation`, `beforeValidate` (update only), `beforeChange`, `afterChange`, `beforeRead`, `afterRead`.
  - **Field-level hooks** (attach to one field's config, fire during the same lifecycle as their parent operation): `beforeValidate`, `beforeChange`, `afterChange`, `afterRead`, plus `beforeDuplicate` (fires before beforeValidate/beforeChange specifically when a document is duplicated — lets a unique field like the slug rewrite itself so duplication doesn't collide).
  - **Root**: `afterError`, app-wide, not scoped to any one collection/global.
  - **Auth hooks dropped, decided**: Payload's six auth-collection hooks (`beforeLogin`, `afterLogin`, `afterLogout`, `afterMe`, `afterRefresh`, `afterForgotPassword`) and its two operation-replacement hooks (`refresh`, `me`) do not apply — auth is delegated entirely to better-auth via `infra`, which owns the whole login lifecycle externally. `Users` is a read-mostly profile extension of better-auth's own user table, not a Payload-style auth-enabled collection. If something ever needs to react to a login, that hook belongs on the `infra`/better-auth side, not as a Demoness collection hook.
  - **Context, confirmed against Payload's `req.context`**: request-scoped, `Record<string, unknown>` by default and extendable via TS declaration merging. Created once when an operation (one create/update/delete/read) starts and passed by reference through every hook that fires during it — collection/global hooks *and* every field-level hook on every field being touched share the **same** context object, not a separately scoped one per field, so a collection `beforeChange` can stash something a field's `afterChange` reads, and vice versa. Three uses, matching Payload: (1) fetch-once/reuse-later across hooks in one operation (e.g. call a 3rd-party API in `beforeChange`, read the result in `afterChange` without refetching), (2) infinite-loop guard — a hook that calls `core`'s own update on its document passes a context flag (e.g. `{ skipAfterChange: true }`) so it doesn't re-trigger itself, (3) passing extra data into an operation from the calling server function/route without inventing a dummy field just to carry it.
- **Plugins, confirmed against Payload's plugin docs**: a plugin is simply `(config) => config` — it receives the incoming Demoness app config and returns a modified one, free to add collections/globals, inject fields into *existing* collections, add hooks, add admin components/routes, add server routes. Registered as an ordered `plugins: [...]` array in the app's top-level config; each plugin transforms the config the previous one produced, and this all runs before validation/sanitization/defaults — same as Payload. Plugins follow the established package convention: folder `demoness-plugin-<name>/`, npm scope `@demoness/plugin-<name>`.
  - **The SEO tab is a plugin, not Pages-specific logic**: `@demoness/plugin-seo`, applied to a list of target collections (e.g. `['pages', 'posts']`), injects a `seo` tab into each — metaTitle/metaDescription/metaImage fields, the auto-generate-from-title hook, the character-count admin UI — all already built in the mockups. Directly modeled on `@payloadcms/plugin-seo`.
  - **The Settings tab's "Parent" field is a plugin too**: `@demoness/plugin-nested-docs`, matching Payload's official Nested Docs plugin — hierarchy + breadcrumb generation, rather than hand-rolled into `core`.
  - **Multi-tenancy (Organization support) is a plugin, decided**: `@demoness/plugin-multi-tenant`, not part of `@demoness/core` — matches Payload's own precedent (Multi-Tenant ships as a separate official plugin) and the earlier decision that multi-tenancy is optional. A single-tenant install never loads this plugin at all, rather than carrying always-present-but-sometimes-inert multi-tenancy code in core.
- **Top-level config: `export default buildConfig({...})`**, confirmed against Payload's config docs and adapted. Directly reused from Payload's shape: `collections`, `globals`, `plugins`, `hooks` (root `afterError`), `db` (required — the `@demoness/d1` adapter), `editor` (our own primitive contentEditable richtext, not Lexical), `secret` (required), `serverURL`, `admin`, `routes` (this is where the `/admin` vs public-root routing decision lives), `endpoints`, `upload` (ties to `@demoness/r2` defaults), `defaultDepth`/`maxDepth` (relationship population depth in API responses), `logger`/`debug`, `onInit`, `indexSortableFields`.
  - **Dropped, deliberately**: `graphQL` (we're server routes + server functions, no GraphQL — decided earlier), `folders`/`queryPresets`/`i18n`/`localization` (not designed yet, future), `telemetry` (not building any).
  - **`sharp` doesn't apply, flagged as a real constraint not a preference**: Payload's `sharp` option assumes Node.js — `sharp` is a native addon and cannot run on the Cloudflare Workers runtime at all. Any image resize/crop in `@demoness/r2` needs a WASM-based library instead (e.g. `@cf-wasm/photon`), not sharp. No decision needed yet, just noted before it's discovered mid-build.
  - **CORS: wide open (`'*'`) by default, decided.** Applies to the public *read* API only (`GET /api/pages/:slug` etc — content delivery, not mutations, which stay behind the admin's authenticated server functions). It's a genuinely public headless content API by design, so no per-consumer whitelist is required to fetch published content cross-origin.
  - **CSRF: kept, decided** — Demoness's own `core` config carries a `csrf` whitelist even though better-auth (via `infra`) owns the actual session-cookie lifecycle. Reasoning: defense in depth — the admin routes independently validate cookie origin rather than trusting better-auth's session handling alone. (Contrast with the auth-hooks decision above, which *were* dropped entirely — CSRF is kept specifically because it's a second independent check, not a duplicate of something better-auth already does.)
  - **Real Payload example confirms the proposed shape needed no changes**: `export default buildConfig({ secret, db: adapter(...), collections: [...] })`, config file conventionally at the project root — matches what was already proposed here.
- **`jobs`, added, optional** — confirmed against Payload's Jobs Queue docs (Tasks: slug + async handler; Workflows: ordered task groups, retry-from-failure; Jobs: queued instances; Queues: named groups, e.g. an `emails` queue running every 10 min vs. a nightly one). Config shape adopted as-is: `jobs: { autoRun: [{ cron, queue, disableScheduling? }], jobsCollectionOverrides }`. **Key divergence, and the reason to actually use it**: Payload's Jobs Queue exists because Node/serverless platforms have no native cron or queue primitives — Cloudflare Workers does (Cron Triggers, Cloudflare Queues), so `@demoness/core`'s `jobs` should be a thin adapter *onto* those platform features rather than reimplementing Payload's own bin-script/polling dispatch mechanism. Tasks/Workflows stay Payload-shaped (familiar, and DB-backed job records still make sense for status/retry visibility); scheduling and dispatch defer to Cron Triggers + Queues. **Not yet verified**: whether Cloudflare Queues is available on the free tier (Cron Triggers themselves are) — check against the free-tier reality-check table above before this becomes load-bearing; if Queues turns out to be Paid-only, `autoRun`'s cron-only path (no queue) may need to be the free-tier default. `jobs` itself is optional — a project with nothing to schedule omits the key entirely, same as `versions`/`drafts` being opt-in per collection.
- **Plugin naming: mirror Payload's official plugin names exactly** (just the scope changes, `@payloadcms` → `@demoness`), confirmed full official list: `plugin-seo`, `plugin-nested-docs`, `plugin-multi-tenant` (all three already matched what was already named above), plus newly identified for the future-candidates list: `plugin-form-builder`, `plugin-search`, `plugin-redirects` (useful once slugs can change), `plugin-sentry`, `plugin-stripe` (Products/ecommerce), `plugin-import-export`, `plugin-mcp` (ties naturally into the unified AI layer). **`plugin-cloud-storage` explicitly not adopted**: that's Payload's swappable-storage-backend abstraction (S3/GCS/Azure/etc.) — Demoness only ever targets R2, so that logic lives baked directly into `@demoness/r2`, not as a separate pluggable-backend plugin.
- **CRUD API shape**, confirmed against Payload's Local API and REST API docs:
  - **REST routes generated per collection/global**: `GET /api/{collection}` (list), `GET /api/{collection}/{id}`, `GET /api/{collection}/count`, `POST /api/{collection}` (create), `PATCH /api/{collection}` (bulk update via `where`) / `PATCH /api/{collection}/{id}`, `DELETE /api/{collection}` (bulk) / `DELETE /api/{collection}/{id}`; globals get only `GET /api/globals/{global}` and `POST /api/globals/{global}` (update — POST, not PATCH, matching Payload's own asymmetry). Query params: `depth`, `select`, `populate`, `limit`, `page`, `sort`, `where`, `joins` (`locale`/`fallback-locale` deferred with localization). Per the earlier CORS decision, only the `GET` routes are the wide-open (`'*'`) public surface — every mutating route requires an authenticated admin session regardless of CORS policy.
  - **Auth-collection routes dropped from `@demoness/core`'s Payload-style per-collection generator** (`/login`, `/logout`, `/me`, `/refresh-token`, `/unlock`, `/verify/:token`, `/forgot-password`, `/reset-password`) — but see the corrected, sourced entry below: this does *not* mean these operations don't exist, only that `core` doesn't need to generate them Payload-style, because better-auth already generates its own equivalent routes natively.
  - **`where` clause: adopt Payload's operator vocabulary as-is** — `equals`, `not_equals`, `greater_than`, `greater_than_equal`, `less_than`, `less_than_equal`, `like`, `contains`, `in`, `not_in`, `exists`, composed via nestable `and`/`or` arrays. Worth knowing and load-bearing for confidence in this choice: **Payload's own SQLite/Postgres adapters are built on Drizzle**, so this operator set already has a proven mapping onto Drizzle query builders — `@demoness/d1` is porting a known-working translation, not inventing one. Dropped: `near`/`within`/`intersects` (geospatial — no `point` field priority yet) and `all` (MongoDB-only, not relevant to D1).
  - **Internal/programmatic API accessor shape, decided**: typed per-collection, not Payload's flat `collection: 'slug'` string-param style. `core.collections.pages.find({ where, sort, limit, page, depth })`, `core.collections.pages.findByID({ id })`, `core.collections.pages.create({ data, user, overrideAccess })`, `core.collections.pages.update({ id, data })` (or bulk via `where`), `core.collections.pages.delete({ id })`, `core.collections.pages.count({ where })`; globals mirror as `core.globals.siteSettings.find()` / `.update({ data })`. Each collection's `data`/`where` shape is fully known to TypeScript through object-property access — no generic `<T>` or slug-string lookup needed to keep type safety, which is the reason this was chosen over Payload's literal shape (more idiomatic for the Zod/TanStack-first design this project already committed to). Options otherwise carried over from Payload's Local API: `depth`, `where`, `sort`, `limit`, `page`, `pagination`, `user`, `overrideAccess`, `showHiddenFields`, plus Demoness's own `context` (see the hooks entry above) in place of Payload's `req`.

## 2026-08-31 — Correction: login/logout/me/refresh-token do exist (auth-routes-dropped was wrong)

The "auth-collection routes dropped" line above was checked against `~/projects/infra`'s actual source (not generic better-auth docs) and turned out to overreach — it's corrected here rather than edited away, per this doc's own rule.

- **Confirmed from `infra`'s real source** (`infra/auth/auth.ts`, `infra/src/routes/api/auth/$.ts`, `accounts/lib/auth-client.ts`, `accounts/middleware/session-middleware.ts`): `infra` runs its own `betterAuth()` mounted at `/api/auth/*` via a TanStack Start catch-all route (`/api/auth/$`) that forwards the raw `Request` straight to `auth.handler(request)` — login, logout, get-session, refresh, etc. are all real, better-auth-native routes there, generated by better-auth itself, not by anything Payload-shaped. `infra` also runs the `oauthProvider()` plugin — it acts as an **OAuth2/OIDC provider** for other products, and `"seer"` is already listed in its `cachedTrustedClients`. Two integration patterns exist in that codebase: direct cookie-sharing via a shared `authClient` + cross-subdomain cookies (used by `accounts`, a same-org trusted subdomain app) vs. a full OAuth2 client flow (the pattern intended for a genuinely separate product — which is what `"seer"` already does). `infra`'s own better-auth instance has **no `organization` plugin** enabled.

## 2026-08-31 — Access control, field-shape correction, and @demoness/ai on TanStack AI

- **Access control, confirmed against Payload's docs, adopted as-is**: functions are scoped per-operation (`read`/`create`/`update`/`delete` on a collection or global; the same shape again at field level for restricting one field independent of the whole document — e.g. only admins can edit a `role` field). A function receives `req` (carrying `user`) plus `id`/`data`/`siblingData`/`blockData`/`doc` depending on context, and returns either a `boolean` or a `Where` query constraint for row-level filtering — e.g. `read: ({ req }) => req.user ? true : { status: { equals: 'published' } }` lets logged-in users see everything while anonymous visitors only see published docs, enforced as a query constraint rather than a post-hoc filter. During the login/session check specifically, doc-scoped args (`id`/`data`/`doc`) are undefined — that's a general-capability check, not a per-document one. Matches the typed-per-collection accessor already decided: `access: {...}` lives inside `defineCollection`/`defineGlobal`.
- **Field-shape correction — real, not a preference change**: Payload fields are **plain objects carrying a `type` string** (`{ name: 'pageTitle', type: 'text', required: true }`), confirmed from Payload's own field docs — not builder-function calls (`text({...})`) as had been assumed and never actually checked in earlier entries here. Resolution, honoring both "follow Payload" and "best suited to TanStack/Zod": `@demoness/fields` still exposes builder functions (`text({...})`, `blocks({...})`, etc.) for ergonomic, type-inferred authoring, but each one **produces that exact Payload-shaped plain object** underneath — so the config a collection actually holds at rest is structurally identical to Payload's (portable mental model, easy to read/serialize/diff), while authoring it reads like idiomatic TanStack/Zod code. The builder function is sugar over the object, not a divergent shape.
- **`@demoness/ai` is built on `@tanstack/ai`, not hand-rolled** — general principle stated and adopted: **TanStack libraries take priority over any other third-party library whenever one is needed**, and TanStack AI fits directly. Confirmed shape: a server route (`chat()` handler in a TanStack Start server route) paired with a client hook (`useChat()`), AG-UI-compliant streaming, official provider adapters including **Gemini** (already matches the earlier provider decision). **Workers AI is not in TanStack AI's official adapter list** — the architecture is provider-extensible, so this needs a custom adapter written for the Workers AI binding, a build task rather than a blocker. `@tanstack/ai-mcp` provides a host-side **MCP client** — kept conceptually distinct from `@demoness/plugin-mcp` (a future MCP *server* exposing `core`'s own CRUD operations as tools to external AI clients like Claude Desktop): complementary, not the same package or the same direction of integration.
- **`@demoness/d1` schema generation, confirmed against Payload's actual Drizzle source** (`packages/drizzle/src/schema/traverseFields.ts` in `payloadcms/payload`), adopted as-is:
  - **`array`** → a dedicated child table: `_order` (integer, sequencing) + `_parent_id` (FK to the parent row, `onDelete: cascade`).
  - **`blocks`** → **one table per block type**, not one shared table — each with `_order`, `_parentID`, and `_path` (tracks nested position, handles blocks-within-blocks/arrays). Table named `{rootTable}_blocks_{blockSlug}`; the parent gets a "many" relation to each block-type table.
  - **`group`** → **no separate table** — flattened into prefixed columns on the same parent table (`groupName_subfieldName`), recursively. Denormalized, not relational.
  - **`relationship`** (single) → a plain FK column (`{field}_id`) on the parent table, `onDelete: set null`. `hasMany` → a junction table.
  - **Naming conventions adopted directly**: `_rels` suffix for relationship junction tables, `_v` for versions (ties into the still-open drafts/versioning storage shape), `_locales` (deferred with localization).
  - **Why join-tables-by-default is an even easier call for Demoness than for Payload itself**: Payload exposes `blocksAsJSON` as an opt-in escape hatch specifically because a typical Payload site queries the database on *every visitor request*, making join overhead on blocks a real hot-path cost. Demoness's whole architecture is cache-first (decided earlier) — D1 is only touched on publish/write, never on normal visitor traffic — so that performance motivation barely applies here. Relational blocks-by-default is the comfortable default for Demoness, not merely the ported one.

## 2026-08-31 — Admin/consumer split, deliberate divergence from Payload's `_rels`, and the `types/` folder correction

- **Admin-UI structure must not leak onto the consumer/data side.** While implementing `@demoness/d1`'s schema builder against `@demoness/fields`' `AnyField`, caught that `BaseField.admin` (and therefore every field object) carried a **mandatory** `component: string` — set by every one of the ~18 builders (`withBase("text", name, "TextInput", ...)`) even though nothing yet read it. That forced any consumer of a field config — `@demoness/d1`'s schema builder, and eventually the public-site renderer — to carry admin-panel-component naming it has no use for. **Fixed**: `FieldAdmin.component` and `BaseField.admin`/`AnyField.admin` are now optional; `withBase` no longer takes a component-name argument at all. Which component renders a given field type is now purely an admin-app concern (a lookup keyed on `field.type`), not something baked onto the field object as a default. The one field type that legitimately keeps a required `component` is `ui` (`field-types/ui.ts`) — its entire purpose *is* being a named slot for a custom admin component, so that's not a leak, it's the field type's actual definition.
- **Types get their own `types/index.ts` folder, never a flat `types.ts`, never declared inline in a `.tsx`.** Re-confirmed against `infra`'s real structure (`infra/infra/domains/auth/types/index.ts`) — `types` is a sibling folder to `config/`/`hooks/`/`views/` at the domain root, not nested inside `config/`. Moved every existing flat `{domain}/config/types.ts` (dashboard, media, pages, site-map, shell) to `{domain}/types/index.ts`, and `packages/demoness-d1/src/schema/types.ts` to `schema/types/index.ts`. Also extracted two inline `.tsx` type declarations that predated this rule being made explicit: `EditChromeProps`/`DocTab`/`FieldTab` out of `pages/views/edit-chrome.view.tsx`, and the admin tab-route's field-tab union (renamed `PageAdminTab`, since it's a different, wider set than `EditChrome`'s own `FieldTab` — it includes `"live-preview"`) out of `routes/admin/$collection/$id/$tab.tsx` — both now live in `domains/pages/types/index.ts`.
- **`@demoness/d1`'s per-field junction tables are a deliberate, documented divergence from Payload's shared `_rels`.** Payload stores every `hasMany` relationship/upload field across a whole collection in **one** polymorphic `_rels` table (parent id, field name, and a set of nullable target-id columns — one per possible related collection). `buildD1Schema` instead builds **one junction table per `hasMany` field** (`${fromTable}_${fieldName}_rels`, a plain `parent_id`/`related_id` pair). Simpler to read and query (no polymorphic nullable-column fan-out, no need to know which target-id column is "live" for a given row), at the cost of one extra table per hasMany field instead of one shared table per collection — an acceptable tradeoff given D1's free-tier table-count headroom and that Demoness collections are hand-authored, not user-defined at scale. Not revisited unless a real multi-collection polymorphic-relationship use case demands it.
- **String primary keys (`text("id").primaryKey()`), not integer autoincrement**, on every generated table — matches Payload's own default (`id` is a generated string, e.g. `pg_8f2ac1` as already used in Stage 1's static mock data) and avoids the cross-collection FK-ordering problems integer autoincrement would create with the worklist/thunk-based table-building approach in `buildD1Schema`.
- **`where`-clause → Drizzle translation, done and tested** (`src/query/where-to-drizzle.ts`): the confirmed operator vocabulary maps onto real, verified `drizzle-orm` exports (`eq`/`ne`/`gt`/`gte`/`lt`/`lte`/`like`/`inArray`/`notInArray`/`isNull`/`isNotNull`/`and`/`or`, checked against the installed package's own `.d.ts`, not guessed). `contains` auto-wraps its value in `%...%` (substring-match sugar); `like` passes the caller's raw pattern through unchanged. Multiple operators on one field, and multiple fields/`and`/`or` keys at the same `Where` level, are implicitly ANDed together — matches Payload's own semantics, verified by rendering actual SQL text via `drizzle-orm/sqlite-core`'s `SQLiteSyncDialect().sqlToQuery()` (no live DB needed) in `__tests__/where-to-drizzle.test.ts`.
- **Migration tooling: investigated, deliberately deferred to Stage 4, not a Stage 3 gap.** Checked `drizzle-kit`'s own bundled source (`prepareFromExports3` in the installed `drizzle-kit@0.31.10`'s `bin.cjs`) to see how its `schema` config option actually loads a schema file — it does `Object.values(moduleExports)` **one level deep** and keeps whatever satisfies `is(value, SQLiteTable)`. That means drizzle-kit can only see **statically, top-level exported table objects** from the schema file it's pointed at. `buildD1Schema`'s output (`{ tables: Record<string, Table> }`, built at runtime from whatever `SchemaSource[]` it's given) can't satisfy that — ESM has no way to turn a runtime record into dynamic named exports. Real migration generation needs a **codegen step**: run `buildD1Schema` against the real collection/global configs and write a literal `.ts` file with one `export const <table> = sqliteTable(...)` per table for drizzle-kit to import — this is, concretely, what Payload's own Drizzle package does under the hood, not a shortcut being skipped here. That codegen step is only meaningful once `@demoness/core` (Stage 4) actually has real collection/global configs to generate from, so it's deferred there rather than faked here with placeholder collections. `packages/demoness-d1/package.json`'s `drizzle-kit` devDependency stays in place for when that lands.

## 2026-09-05 (later still) — 1A corrected: dispatch moved from an in-component hook into a real TanStack `loader`, URL scheme flattened

## 2026-09-05 (final) — the nested-router design built for real, two real bugs found only by testing, one accepted gap

User confirmed via the two follow-up mid-turn messages ("yes both ssr and client" / "during ssr") that SSR-loader execution is a hard requirement, then asked directly to try the nested-router approach empirically rather than fall back to the safer design, once the earlier globals-prefix correction had resolved the sibling-route ambiguity. Built exactly to the corrected plan, then verified against the real dev server — and the first attempt genuinely did not work, exactly the risk that had been flagged going in:

- **First real bug, found by testing, not by reasoning about the API**: `use(loadPromise)` called directly inside `AdminRouterMount` with no ancestor `<Suspense>` boundary produced **completely empty output on every single route**, including the dashboard — no error, no fallback, nothing after `</header>` in the raw SSR HTML. `use()` needs a Suspense boundary *above* the component that calls it; a component can't wrap its own `use()` call in a `<Suspense>` and have that catch its own suspension. Fixed by splitting into an inner `AdminRouterInner` (calls `use()`) wrapped by the outer `AdminRouterMount` in `<Suspense fallback={null}>`.
- **Second real bug, also found only by testing**: after the Suspense fix, `/admin/pages`, `/admin/pages/abc123`, and `/admin/globals/headers` all rendered correctly — but `/admin` (the dashboard) alone still rendered empty. Root cause: the fallback path fed to `createMemoryHistory({ initialEntries: [...] })` on the server was `/admin` (no trailing slash); after `basepath: '/admin'` stripping, that leaves an empty string, which didn't match the dashboard route's `path: '/'`. Fixed by seeding `/admin/` (trailing slash) instead — confirmed via a direct before/after `curl` that this was exactly the cause, not a guess left unverified.
- **A stray "makes no sense" moment mid-debugging that was actually a stale dev server, not a new bug**: after a batch of file deletions (`route.tsx`, `types.ts`, `get-route-data.ts`), the dev server briefly threw `Failed to load url .../route.tsx` — a Vite module-graph reference to a file already removed from `views/index.ts`, just not yet invalidated. A full `bun run dev` restart (not a source fix) cleared it; confirmed via a fresh `tsc --noEmit` that the actual current source had no such reference.
- **Real evidence the original bundle-size goal was actually achieved**, not just structurally plausible: `tsdown`'s build log showed separate output chunks per lazy-loaded view (`documents-*.mjs`, `document-editor-*.mjs`, `global-editor-*.mjs`, `collection-list-*.mjs`, plus a tiny standalone `data-*.mjs` for the `collections`/`globals` arrays extracted specifically so `route-tree.ts`'s loaders don't have to eagerly pull in the `Documents` component's own code just to validate a slug) — this is the concrete mechanism that answers "too many requests for things you haven't loaded" from the start of this whole sub-stage.
- **One gap accepted, not silently dropped**: the nested router's `notFound()` throw renders correctly (TanStack's own default `<p>Not Found</p>`, since no custom `notFoundComponent` was configured) but the *outer* HTTP response for a bad slug still comes back 200, not 404 — the nested router's not-found state has no path back to the real outer file-route's response status. Recorded as a known, accepted limitation in `docs/PLAN.md`, not fixed, since it's lower-stakes for an authenticated admin panel than it would be for public content.
